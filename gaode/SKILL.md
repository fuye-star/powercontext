# 周边去哪儿：基于高德的地点推荐助手

## 这个 Skill 用来做什么

把用户的一句自然语言需求，变成一份**可核对的周边推荐清单**：

- 用户输入：城市、起点（通常是明确经纬度，也可能是一句地名描述）、需求（地点类型、步行时间上限、推荐数量、排序偏好）。
- 你输出：最多 3 个地点，每个都有**高德返回的真实名称与地址**、**步行路线查询得到的距离与预计时间**，以及一句有数据依据的推荐理由。

硬性要求：地点和路线数据必须来自高德 MCP 工具的真实返回；不得编造地点、地址、距离或时间；不得用直线距离冒充满意步行时间。

## 可用工具（高德 MCP Server）

| 工具 | 用途 | 关键参数 |
| --- | --- | --- |
| `maps_geo` | 结构化地址/地名 → 经纬度 | `address`，可选 `city` |
| `maps_text_search` | 关键字搜索 POI | `keywords`，可选 `city`、`types` |
| `maps_around_search` | **周边搜索**（首选） | `location`（必填，`经度,纬度`）、`keywords`、`radius`（米） |
| `maps_search_detail` | 按 POI ID 取详情 | `id` |
| `maps_direction_walking` | **步行路线规划**（必用） | `origin`、`destination`（均为 `经度,纬度`） |
| `maps_distance` | 距离测量（仅作辅助参考） | `origins`、`destination`、`type`（`1` 驾车 / `0` 直线 / `3` 步行） |

注意事项：

- 坐标格式一律是 `经度,纬度`（先经度后纬度），不要反过来。
- 步行时间**只能**取自 `maps_direction_walking` 返回的路径耗时；`maps_distance` 的直线距离不能当作步行距离，也不能用来推断“步行 X 分钟”。
- 工具名若与上表略有差异，选择语义最接近的“周边/关键字搜索”和“步行路径规划”工具，不要改用驾车或公交路线替代步行。

## 执行流程

### 第 1 步：解析需求

从用户输入中提取：

1. **城市**：如“杭州”“上海”。缺省时从起点描述或周边搜索结果中推断，但不要编造。
2. **起点坐标**：评测通常直接给出经纬度（形如 `120.15,30.28` 或 `120.15, 30.28`）。
3. **地点类型**：咖啡馆、餐厅、公园、便利店、药店等，转成适合搜索的关键词（见第 2 步的关键词表）。
4. **步行时间上限**：如“步行不超过 15 分钟”。没有提及时不设硬性上限，但仍要给出步行时间。
5. **推荐数量**：如“最多 3 家”。没有提及时默认最多 3 个。
6. **排序偏好**：如“优先近一点”→ 按步行时间/距离升序。

如果用户只给了地名（例如“杭州东站”“西湖文化广场地铁站”），先用 `maps_geo`（必要时配合 `city`）把地名解析成经纬度：

```text
maps_geo(address="杭州东站", city="杭州")
→ 取返回的第一个经纬度作为起点，并在回答里说明起点是解析得到的
```

解析失败时尝试 `maps_text_search(keywords="杭州东站", city="杭州")`，从结果里取坐标；两者都失败就如实说明无法定位起点，并请用户提供经纬度。

### 第 2 步：周边搜索候选

以起点为中心调用 `maps_around_search`：

```text
maps_around_search(location="<起点经度>,<起点纬度>", keywords="咖啡", radius="1500")
```

关键词建议：

| 用户说法 | 搜索关键词 |
| --- | --- |
| 咖啡馆 / 咖啡店 | 咖啡 |
| 餐厅 / 吃饭 | 美食 或 餐厅 |
| 公园 / 绿地 | 公园 |
| 便利店 / 超市 | 便利店 或 超市 |
| 药店 | 药店 |
| 景点 | 景点 |

半径策略（`radius` 单位米，字符串）：

1. 初始半径按步行时间上限估算：`radius ≈ 步行分钟数 × 80`，下限 500，上限 3000；用户没给时间上限时用 1000。
2. 若符合条件的候选少于用户要的数量，把半径扩大一档（如 1500 → 2500 → 3000）再搜一次。
3. 扩大后仍不足，或用户的时间上限极严（如 ≤5 分钟），如实说明“该范围内符合条件的只有 N 个”，并建议放宽时间或半径。

候选不足时的兜底：用 `maps_text_search(keywords="<关键词>", city="<城市>")` 补充候选，但只保留起点附近的（可用 `maps_distance` 的步行类型 `type="3"` 粗筛，最终仍以 `maps_direction_walking` 为准）。

从搜索结果里整理候选 POI：名称、地址、经纬度（`location`）、类型（`type`）、POI ID。按“名称 + 地址”去重，去掉明显不符合需求类型的结果。

### 第 3 步：逐个查询步行路线

对每个候选（建议先取最近的 6–10 个，避免不必要的调用）调用：

```text
maps_direction_walking(origin="<起点经度>,<起点纬度>", destination="<候选经度>,<候选纬度>")
```

从返回的 `paths[0]` 取：

- 步行距离：`paths[0].distance`（米）；
- 预计时间：`paths[0].duration`（秒，换算成分钟并向上取整）。

如果 `paths` 为空或工具报错：

- 重试一次；
- 仍失败则跳过该候选，并在回答末尾说明“有 N 个候选的步行路线查询失败，未纳入推荐”。

### 第 4 步：筛选、排序、取前 3

1. **时间过滤**：只保留步行时间 ≤ 用户上限的地点。超过上限的地点**不能**放进推荐列表；如果需要说明“附近还有更远的选择”，单独用一句话提及并明确标注超出上限。
2. **排序**：用户说“优先近一点”或没有特别偏好时，按步行时间升序（同时间再按距离升序）。若用户明确要求其他偏好（如“环境好”），只在与数据不冲突时调整，并说明排序依据。
3. **截断**：最多返回用户要求的数量（没有要求时最多 3 个）。
4. **理由**：每个地点一句理由，必须能对应到工具数据，例如“步行 6 分钟、约 450 米，是本次候选中最近的咖啡馆”。不要写没有依据的“安静”“不用排队”“环境很好”。

### 第 5 步：组织回答

用表格或列表呈现，字段固定：

| 地点 | 地址 | 步行距离 | 步行时间 | 推荐理由 |
| --- | --- | --- | --- | --- |
| 名称（来自高德） | 地址（来自高德） | 450 米 | 约 6 分钟 | 本次候选中最接近起点，步行 6 分钟可达 |

表格之后补一句简短说明：

- 起点：`经度,纬度`（如果是地名解析得到，注明“由‘杭州东站’解析得到”）；
- 搜索半径与筛选条件（如“1.5 公里内、步行 ≤15 分钟”）；
- 未核实信息：营业状态、排队情况、安静程度等一律标注“未核实”；
- 结果不足的原因或建议（如“该范围内 15 分钟内只有 2 家咖啡馆，可把时间放宽到 20 分钟”）；
- 工具失败说明（如有）。

最终回答只保留用户需要的信息，不要堆砌原始 JSON，也不要输出坐标列表以外的工具调用细节。

## 结果不理想时怎么处理

| 情况 | 处理方式 |
| --- | --- |
| 周边搜索无结果 | 换更宽的关键词（“咖啡”→ “咖啡厅/饮品”），或扩大半径重试一次；仍无结果就如实说明“该范围未找到符合条件的地点”，并建议放宽类型或范围 |
| 符合时间上限的不足 3 个 | 只推荐符合条件的，明确说“符合条件的只有 N 个”，并给出放宽建议；不要用超时地点补足数量 |
| 步行路线查询失败 | 重试一次；仍失败则排除该点并说明，不得用直线距离估算时间 |
| 用户没给时间上限 | 不设硬性过滤，但仍要查步行路线并展示时间 |
| 用户给的信息有歧义 | 按最合理的解释执行，并在回答里说明假设（如“按‘咖啡馆’理解”），不要反问后停住 |
| 起点无法解析 | 如实说明并请用户提供经纬度，不要编造起点 |

## 禁止事项

- 不得编造地点、地址、坐标、距离或步行时间；所有数值必须来自工具返回。
- 不得用 `maps_distance` 的直线距离或“大约几分钟”替代 `maps_direction_walking` 的步行时间。
- 不得把超过步行时间上限的地点列为“符合条件的推荐”。
- 不得声称营业中、无需排队、环境安静等未经工具核实的信息。
- 不得把多个地点串成一条多站行程；每个推荐都是从同一起点出发的独立备选。
- 不要在 Skill 或回答中写入、索取或暴露任何高德 API Key。
